Clean Architecture

Dela upp koden i lager där beroenden alltid pekar inåt mot domänen. Domänen ska inte känna till EF Core, ASP.NET eller något ramverk.

Lagerstruktur

Presentation (API)  →  Infrastructure  →  Application  →  Domain
        Beroenden pekar alltid INÅT ───────────────────────►
LagerAnsvarFår bero på
DomainEntiteter, value objects, affärsreglerIngenting (rent C#)
ApplicationUse cases, CQRS-handlers, interfacesDomain
InfrastructureEF Core, repositories, externa tjänsterApplication, Domain
Presentation/APIControllers, endpoints, DI-setupApplication, Infrastructure

Exempel — domänentitet utan ramverksberoenden

// Domain/Entities/Order.cs
public class Order
{
    public Guid Id { get; private set; }
    public string CustomerName { get; private set; }
    public OrderStatus Status { get; private set; }

    private readonly List<OrderItem> _items = new();
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();

    private Order() { } // EF Core

    public Order(string customerName)
    {
        Id = Guid.NewGuid();
        CustomerName = customerName;
        Status = OrderStatus.Pending;
    }

    // Affärsregeln bor i domänen — inte i en controller
    public void Confirm()
    {
        if (!_items.Any())
            throw new DomainException("Cannot confirm an order without items.");
        Status = OrderStatus.Confirmed;
    }
}
Varför: Kärnlogiken isoleras från teknik som byts ut ofta. Du kan byta databas eller ramverk utan att röra affärsreglerna — koden blir testbar, hållbar och lätt att resonera om.

Dependency Injection (DI)

Koppla in beroenden via konstruktorn istället för new. Varje lager exponerar en egen AddXxx-extension för att hålla Program.cs ren.

Registrering per lager

// Application/DependencyInjection.cs
public static IServiceCollection AddApplication(this IServiceCollection services)
{
    services.AddMediatR(cfg =>
        cfg.RegisterServicesFromAssembly(typeof(DependencyInjection).Assembly));
    services.AddValidatorsFromAssembly(typeof(DependencyInjection).Assembly);
    services.AddTransient(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));
    return services;
}

// Program.cs
builder.Services
    .AddApplication()
    .AddInfrastructure(builder.Configuration)
    .AddPresentation();

FluentValidation

Validera inkommande data deklarativt istället för spridda if-satser. Validatorn ligger bredvid sin command och körs automatiskt via en MediatR-behavior.

Validator

public class CreateOrderValidator : AbstractValidator<CreateOrderCommand>
{
    public CreateOrderValidator()
    {
        RuleFor(x => x.CustomerName)
            .NotEmpty().WithMessage("Customer name is required.")
            .MaximumLength(100);

        RuleFor(x => x.Items)
            .NotEmpty().WithMessage("An order must contain at least one item.");

        RuleForEach(x => x.Items).ChildRules(item =>
        {
            item.RuleFor(i => i.Quantity).GreaterThan(0);
            item.RuleFor(i => i.Price).GreaterThanOrEqualTo(0);
        });
    }
}

Automatisk körning via pipeline behavior

public class ValidationBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse> where TRequest : notnull
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;
    public ValidationBehavior(IEnumerable<IValidator<TRequest>> validators)
        => _validators = validators;

    public async Task<TResponse> Handle(TRequest request,
        RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var context = new ValidationContext<TRequest>(request);
        var failures = _validators
            .Select(v => v.Validate(context))
            .SelectMany(r => r.Errors)
            .Where(f => f is not null)
            .ToList();

        if (failures.Any())
            throw new ValidationException(failures);

        return await next();
    }
}
Varför: Validering blir centraliserad, läsbar och testbar. Handlern kan utgå från att datan är giltig. Behavior-mönstret gör att du aldrig glömmer att köra valideringen.

CQRS & MediatR

Skilj skrivoperationer (Commands) från läsoperationer (Queries). MediatR skickar varje request till exakt en handler och håller controllers tunna.

// Command — ändrar state
public record CreateOrderCommand(string CustomerName, List<OrderItemDto> Items)
    : IRequest<Guid>;

public class CreateOrderHandler : IRequestHandler<CreateOrderCommand, Guid>
{
    private readonly IOrderRepository _repository;
    private readonly IUnitOfWork _unitOfWork;

    public CreateOrderHandler(IOrderRepository repository, IUnitOfWork unitOfWork)
    {
        _repository = repository;
        _unitOfWork = unitOfWork;
    }

    public async Task<Guid> Handle(CreateOrderCommand request, CancellationToken ct)
    {
        var order = new Order(request.CustomerName);
        foreach (var item in request.Items)
            order.AddItem(item.ProductId, item.Quantity, item.Price);

        await _repository.AddAsync(order, ct);
        await _unitOfWork.SaveChangesAsync(ct);
        return order.Id;
    }
}

// Controllern blir tunn — den delegerar bara
[ApiController]
[Route("api/orders")]
public class OrdersController : ControllerBase
{
    private readonly ISender _mediator;
    public OrdersController(ISender mediator) => _mediator = mediator;

    [HttpPost]
    public async Task<IActionResult> Create(CreateOrderCommand command)
    {
        var id = await _mediator.Send(command);
        return CreatedAtAction(nameof(GetById), new { id }, id);
    }
}
Varför: Command/query-separation ger ett enda ansvar per handler (SRP), gör use cases lätta att hitta och testa, och möjliggör cross-cutting concerns (validering, loggning) via behaviors. Controllers fokuserar bara på HTTP.

Felhantering & Result-mönster

Använd ett Result-mönster för förväntade fel och exceptions bara för verkligt oväntade — plus en global middleware som mappar fel till HTTP-svar.

// Result-mönster för förväntade utfall
public class Result<T>
{
    public bool IsSuccess { get; }
    public T? Value { get; }
    public string? Error { get; }

    private Result(bool ok, T? value, string? error)
        => (IsSuccess, Value, Error) = (ok, value, error);

    public static Result<T> Success(T value) => new(true, value, null);
    public static Result<T> Failure(string error) => new(false, default, error);
}

// Global middleware mappar exceptions → ProblemDetails (RFC 7807)
public class ExceptionHandlingMiddleware
{
    private readonly RequestDelegate _next;
    public ExceptionHandlingMiddleware(RequestDelegate next) => _next = next;

    public async Task InvokeAsync(HttpContext context)
    {
        try { await _next(context); }
        catch (ValidationException ex)
        {
            context.Response.StatusCode = StatusCodes.Status400BadRequest;
            await context.Response.WriteAsJsonAsync(new ProblemDetails
            {
                Title = "Validation failed",
                Detail = string.Join("; ", ex.Errors.Select(e => e.ErrorMessage))
            });
        }
        catch (NotFoundException ex)
        {
            context.Response.StatusCode = StatusCodes.Status404NotFound;
            await context.Response.WriteAsJsonAsync(new ProblemDetails { Title = ex.Message });
        }
    }
}
Varför: Konsekvent felhantering ger förutsägbara API-svar och slipper upprepad try/catch. Result gör förväntade fel explicita i signaturen. ProblemDetails är en standard som din React-frontend kan hantera enhetligt.

Repository & Persistence

Abstrahera databasåtkomst bakom interfaces som definieras i Application och implementeras i Infrastructure. EF-konfiguration i egna klasser.

// Application/Common/Interfaces/IOrderRepository.cs (abstraktion i Application)
public interface IOrderRepository
{

// Infrastructure/Persistence/Configurations/OrderConfiguration.cs
public class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> builder)
    {
        builder.HasKey(o => o.Id);
        builder.Property(o => o.CustomerName).IsRequired().HasMaxLength(100);

Varför: Interfaces i Application + implementation i Infrastructure respekterar beroenderiktningen. Separata IEntityTypeConfiguration-klasser håller DbContext ren utan att förorena domänen.

Tester

Tester är ett krav. Använd AAA-mönstret (Arrange–Act–Assert) och en testpyramid: många snabba unit-tester, färre integration, ännu färre E2E.

Unit-test (xUnit + FluentAssertions + Moq)

public class CreateOrderHandlerTests
{
    [Fact]
    public async Task Handle_WithValidItems_CreatesOrderAndReturnsId()
    {
        // Arrange
        var repo = new Mock<IOrderRepository>();
        var uow = new Mock<IUnitOfWork>();
        var handler = new CreateOrderHandler(repo.Object, uow.Object);
        var command = new CreateOrderCommand("Anna",
            new() { new OrderItemDto(Guid.NewGuid(), 2, 50m) });

        // Act
        var result = await handler.Handle(command, CancellationToken.None);

        // Assert
        result.Should().NotBeEmpty();
        repo.Verify(r => r.AddAsync(It.IsAny<Order>(), It.IsAny<CancellationToken>()), Times.Once);
        uow.Verify(u => u.SaveChangesAsync(It.IsAny<CancellationToken>()), Times.Once);

Authentication & Authorization

Authentication = vem är du (JWT bearer tokens). Authorization = vad får du göra (roller & policies). Obligatoriskt i varje system som säljs till kund.

JWT-konfiguration & policies

// Program.cs
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidIssuer = builder.Configuration["Jwt:Issuer"],
            ValidAudience = builder.Configuration["Jwt:Audience"],
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(builder.Configuration["Jwt:Key"]!))
        };
    });

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
    options.AddPolicy("CanManageOrders", p => p.RequireClaim("permission", "orders:write"));
});

app.UseAuthentication();   // ordning spelar roll
app.UseAuthorization();

Skydda endpoints

[Authorize(Policy = "CanManageOrders")]
[HttpPost]
public async Task<IActionResult> Create(CreateOrderCommand command) { ... }

[Authorize(Roles = "Admin")]
[HttpDelete("{id}")]
public async Task<IActionResult> Delete(Guid id) { ... }
Varför: Policy-baserad auktorisering (istället för hårdkodade rollkontroller i koden) gör behörigheter centraliserade och lätta att ändra utan att röra affärslogik. Validering av issuer/audience/lifetime skyddar mot förfalskade och utgångna tokens. Använd refresh tokens för längre sessioner och hasha lösenord med t.ex. ASP.NET Identity / BCrypt.

Serilog — strukturerad loggning

Varför: Strukturerade loggar (JSON) går att söka och filtrera i verktyg som Seq/Elastic/Application Insights — råa textsträngar gör inte det. Pagination, filtrering & sortering

Returnera aldrig hela tabeller. Sidindela, filtrera och sortera på databasnivå (IQueryable) så att svaren förblir snabba även när kundens data växer.

public record PagedResult<T>(IReadOnlyList<T> Items, int Page, int PageSize, int TotalCount)
{
    public int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);
}

public async Task<PagedResult<OrderDto>> Handle(GetOrdersQuery q, CancellationToken ct)
{
    var query = _db.Orders.AsNoTracking();

    // Filtrering
    if (!string.IsNullOrWhiteSpace(q.Search))
        query = query.Where(o => o.CustomerName.Contains(q.Search));

    // Sortering
    query = q.SortBy == "total"
        ? query.OrderByDescending(o => o.Total)
        : query.OrderBy(o => o.CreatedAt);

    var total = await query.CountAsync(ct);

    // Pagination — körs i databasen, inte i minnet
    var items = await query
        .Skip((q.Page - 1) * q.PageSize)
        .Take(q.PageSize)
        .Select(o => o.ToDto())
        .ToListAsync(ct);

    return new PagedResult<OrderDto>(items, q.Page, q.PageSize, total);
}
Varför: Utan pagination växer svarstiden och minnesanvändningen linjärt med datamängden — det som funkar i demo kraschar hos en stor kund. Skip/Take + AsNoTracking gör att databasen gör jobbet och bara nödvändiga rader hämtas. Begränsa alltid maximalt PageSize så att klienten inte kan begära allt.

Caching

Cacha dyra eller ofta lästa data för att minska databaslast och svarstid. IMemoryCache för en instans, distribuerad cache (Redis) när du kör flera instanser.

// Cache-aside-mönstret med distribuerad cache (Redis)
public async Task<ProductDto> GetProductAsync(Guid id, CancellationToken ct)
{
    var key = $"product:{id}";
    var cached = await _cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<ProductDto>(cached)!;

    var product = await _repository.GetByIdAsync(id, ct);
    var dto = product.ToDto();

    await _cache.SetStringAsync(key, JsonSerializer.Serialize(dto),
        new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10) }, ct);

    return dto;
}

// Invalidera vid ändring
await _cache.RemoveAsync($"product:{id}", ct);
Varför: Caching är ofta den enskilt största prestandavinsten. Distribuerad cache (Redis) krävs när appen skalas till flera instanser/poddar — annars blir cachen inkonsekvent mellan instanserna. Sätt alltid en expiration och en tydlig invalidation-strategi, annars serverar du gammal data.

Configuration & Secrets

Konfiguration per miljö (dev/test/prod) via Options-mönstret, och hemligheter (connection strings, API-nycklar) i en säker secret store — aldrig i koden eller i checkad-in appsettings.json.

// Typad konfiguration (Options-mönstret)
public class JwtOptions
{
    public string Issuer { get; init; } = default!;
    public string Audience { get; init; } = default!;
    public int ExpiryMinutes { get; init; }
}

builder.Services
    .AddOptions<JwtOptions>()
    .Bind(builder.Configuration.GetSection("Jwt"))
    .ValidateDataAnnotations()

// Injicera typat
public AuthService(IOptions<JwtOptions> options) => _jwt = options.Value;

Hemligheter per miljö: dotnet user-secrets (lokalt) · environment-variabler / Azure Key Vault / AWS Secrets Manager (prod). appsettings.Development.json vs appsettings.Production.json för icke-hemlig config.

Varför: Options-mönstret ger typad, validerad config med ValidateOnStart så att appen kraschar direkt vid felaktig konfiguration istället för halvvägs in i produktion. Hemligheter i en secret store (inte i repo) är ett säkerhets- och GDPR-krav — läckta nycklar i Git är en av de vanligaste incidenterna.

Säkerhet (CORS, rate limiting, headers)

Grundläggande säkerhetslager varje kund förväntar sig: CORS, rate limiting, säkerhetsheaders, HTTPS och skydd mot OWASP Top 10.

// CORS — tillåt bara kända origins (aldrig AllowAnyOrigin i prod)
builder.Services.AddCors(o => o.AddPolicy("Frontend", p => p
    .WithOrigins("https://app.kund.se")
    .AllowAnyHeader()
    .AllowAnyMethod()
    .AllowCredentials()));

// Rate limiting — skydd mot missbruk / brute force
builder.Services.AddRateLimiter(o => o.AddFixedWindowLimiter("api", opt =>
{
    opt.Window = TimeSpan.FromMinutes(1);
    opt.PermitLimit = 100;
}));

app.UseHttpsRedirection();
app.UseCors("Frontend");
app.UseRateLimiter();

OWASP-grunder: parametriserade queries / EF (skydd mot SQL-injection) · validering av all input · inga interna fel/stack traces till klient · säkerhetsheaders (HSTS, X-Content-Type-Options, CSP) · principen om minsta behörighet.

Varför: Ett system som säljs till kund granskas ofta i en säkerhetsrevision. CORS hindrar obehöriga webbplatser från att anropa ditt API i användarens namn. Rate limiting skyddar mot brute force och DoS. Dessa lager är billiga att lägga till tidigt men dyra att eftermontera efter en incident.

Background jobs & resiliens

Tunga eller schemalagda uppgifter körs i bakgrunden (inte i request-tråden), och anrop till externa tjänster skyddas med retry & circuit breaker (Polly).

Background jobs (Hangfire eller IHostedService)

// Schemalagt / köat jobb med Hangfire
BackgroundJob.Enqueue<IEmailService>(s => s.SendOrderConfirmationAsync(orderId));
RecurringJob.AddOrUpdate<IReportService>("nightly",
    s => s.GenerateDailyReportAsync(), Cron.Daily);

Resiliens med Polly

builder.Services.AddHttpClient<IPaymentClient, PaymentClient>()
    .AddPolicyHandler(HttpPolicyExtensions
        .HandleTransientHttpError()
        .WaitAndRetryAsync(3, attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt))))  // exponential backoff
    .AddPolicyHandler(HttpPolicyExtensions
        .HandleTransientHttpError()
        .CircuitBreakerAsync(5, TimeSpan.FromSeconds(30)));   // bryt vid upprepade fel
Varför: Att skicka mejl eller generera rapporter i request-tråden gör API:t långsamt och bräckligt — flytta det till bakgrunden. Externa tjänster kommer att fela ibland; retry med exponential backoff och circuit breaker gör systemet motståndskraftigt istället för att en tillfällig störning sprider sig till hela appen.

CI-pipeline (steg)

1. restore + build
2. kör unit-, integration- och arkitekturtester   ← bygget faller om något test failar
3. scanna beroenden för sårbarheter
4. bygg & pusha Docker-image (taggad med commit/version)
5. deploy till Staging → automatiska smoke tests → Production
6. databasmigrationer körs kontrollerat vid deploy
Varför: Manuell deploy är felkällan nr 1 i produktion. En pipeline som kör alla tester och säkerhetsscanning vid varje commit gör releaser förutsägbara och spårbara — du kan alltid se exakt vad som deployats och rulla tillbaka. Containers ger identisk miljö lokalt, i test och i prod ("works on my machine" försvinner).

Props

Props är read-only data som skickas från förälder till barn. Typa dem alltid. Mutera aldrig props.

type ButtonProps = {
  label: string;
  variant?: "primary" | "secondary";   // valfri prop med union-typ
  disabled?: boolean;
  onClick: () => void;
};

export function Button({ label, variant = "primary", disabled = false, onClick }: ButtonProps) {

    <button className={`btn btn--${variant}`} disabled={disabled} onClick={onClick}>

Regler: destrukturera props i parameterlistan · ge defaultvärden för valfria props · använd union-typer istället för lösa strängar · skicka funktioner ner som callbacks för att kommunicera uppåt.

Varför: Typade props är ett kontrakt mellan komponenter — TypeScript fångar fel innan körning. Att props är read-only gör dataflödet enkelriktat och förutsägbart.

State

State är data som ändras över tid och som komponenten äger. useState för enkelt, useReducer för komplext. Lyft state till närmaste gemensamma förälder när flera behöver dela det.

// Enkelt lokalt state
const [count, setCount] = useState(0);

// Uppdatera baserat på föregående värde — funktionsformen
setCount(prev => prev + 1);

// Objekt-state: skapa NY referens (mutera aldrig direkt)
const [form, setForm] = useState({ name: "", email: "" });
setForm(prev => ({ ...prev, name: "Anna" }));   // ✅ ny referens
// form.name = "Anna";                            // ❌ muterar — React renderar inte om

// Komplext state med useReducer
type State = { items: Item[]; loading: boolean };
type Action = { type: "loaded"; items: Item[] } | { type: "loading" };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "loading": return { ...state, loading: true };
    case "loaded":  return { items: action.items, loading: false };
  }
}
const [state, dispatch] = useReducer(reducer, { items: [], loading: false });

Regler: mutera aldrig state direkt · använd funktionsformen vid uppdatering baserad på gammalt värde · härled värden under render istället för att spara dem · håll state så lokalt som möjligt.

Varför: React jämför referenser för att avgöra om något ändrats. Muterar du state direkt ändras inte referensen → ingen omrendering → buggar. Härledda värden istället för dubbellagring förhindrar osynk.

Events

Hantera interaktioner med event handlers. Namnge handlern handleXxx och prop:en onXxx. Typa eventet.

export function SearchBox({ onSearch }: { onSearch: (term: string) => void }) {
  const [term, setTerm] = useState("");

  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    setTerm(e.target.value);
  };

  const handleSubmit = (e: React.FormEvent<HTMLFormElement>) => {
    e.preventDefault();              // glöm inte detta på formulär
    onSearch(term);
  };

  return (
    <form onSubmit={handleSubmit}>
      <input value={term} onChange={handleChange} placeholder="Sök..." />
      <button type="submit">Sök</button>
    </form>
  );
}

Regler: skicka funktionsreferens onClick={handleClick}, inte anrop onClick={handleClick()} · behöver du argument: onClick={() => handleDelete(id)} · barn kommunicerar uppåt genom callback-props.

Varför: Konsekvent handle/on-namngivning gör koden förutsägbar. Skickar du anrop istället för referens körs det vid varje render — en vanlig bugg. Callbacks uppåt håller dataflödet enkelriktat (data ner, events upp).

useEffect

useEffect är till för sidoeffekter — synk med system utanför React (API, prenumerationer, timers). Det är inte till för att beräkna värden under render.

useEffect(() => {
  const controller = new AbortController();

  async function loadOrders() {
    const res = await fetch("/api/orders", { signal: controller.signal });
    setOrders(await res.json());
  }
  loadOrders();

  // Cleanup — körs före nästa effekt och vid unmount
  return () => controller.abort();
}, [/* dependencies */]);   // [] = en gång · [id] = när id ändras

[]Kör en gång vid mount
[id, filter]Kör vid mount + när någon dependency ändras
utelämnadKör vid varje render — nästan alltid fel
Varför: Fel dependency-array ger antingen oändliga loopar eller inaktuell data (stale closures). Cleanup förhindrar minnesläckor och att ett gammalt svar skriver över ett nyare.

Villkorlig rendering

Rendera olika UI beroende på state/props. Hantera alla tillstånd: loading, fel, tomt och data.

function OrderList({ orders, isLoading, error }: OrderListProps) {

Listor & keys

Rendera listor med .map(). Varje element måste ha en stabil, unik key — ett riktigt ID, aldrig array-index om listan kan ändras.

{orders.map(order => (
  <OrderCard key={order.id} customerName={order.customerName} total={order.total} />
))}

// ❌ Undvik index som key vid dynamiska listor
{orders.map((order, index) => <OrderCard key={index} {...order} />)}

Regler: key ska vara stabil och unik (oftast item.id) · sätts på det yttersta elementet i map · bryt ut komplex item-rendering till egen komponent · använd .map()/.filter()/.slice() som returnerar nya arrayer.

Varför: React använder key för reconciliation (vilka element ändrats/lagts till/tagits bort). Index-keys orsakar buggar när listan ändras — React kan återanvända fel DOM-element, vilket ger fel state i inputs. Stabila ID-keys ger korrekta och effektiva uppdateringar.

Custom hooks

Bryt ut återanvändbar logik (data-hämtning, formulär) till custom hooks — en funktion som börjar på use och får använda andra hooks.

// hooks/useOrders.ts
export function useOrders() {
  const [orders, setOrders] = useState<Order[]>([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    fetch("/api/orders", { signal: controller.signal })
      .then(res => res.json())
      .then(setOrders)
      .catch(err => { if (err.name !== "AbortError") setError(err.message); })
      .finally(() => setIsLoading(false));
    return () => controller.abort();
  }, []);

  return { orders, isLoading, error };
}

// Användning — komponenten blir ren och deklarativ
function OrdersPage() {
  const { orders, isLoading, error } = useOrders();
  return <OrderList orders={orders} isLoading={isLoading} error={error} />;
}
Varför: Custom hooks separerar logik från UI — komponenter blir rena och logiken återanvändbar och testbar. Samma data-hämtning kan användas på flera sidor utan duplicering.

Server-state (React Query / TanStack Query)

Skilj server-state (data från API:t) från client-state (UI-tillstånd). Använd TanStack Query för hämtning, cachning, refetch och mutationer — sluta bygga det själv med useEffect.

// Query — hämtning med cache, loading & error inbyggt
function useOrders() {
  return useQuery({
    queryKey: ["orders"],
    queryFn: () => api.get<Order[]>("/orders").then(r => r.data),
    staleTime: 60_000,           // anses färsk i 1 min
  });
}

// Mutation — skapa + invalidera cachen så listan uppdateras
function useCreateOrder() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (dto: CreateOrderDto) => api.post("/orders", dto),
    onSuccess: () => qc.invalidateQueries({ queryKey: ["orders"] }),
  });
}

// Användning — ren komponent
function OrdersPage() {
  const { data: orders = [], isLoading, error } = useOrders();
  if (isLoading) return <Spinner />;
  if (error) return <ErrorMessage />;
  return <OrderList orders={orders} />;
}
Varför: Server-state har helt andra behov än client-state: cachning, dedupering, bakgrunds-refetch, retry och invalidation. Att lösa det manuellt med useEffect + useState i varje komponent blir buggigt och repetitivt. TanStack Query ger allt detta deklarativt och är närmast standard i stora React-projekt.

Forms & validering

Formulär är där de flesta buggar bor. Använd React Hook Form för prestanda och Zod för schema-baserad, typsäker validering.

// Zod-schema = validering + TypeScript-typ från en källa
const orderSchema = z.object({
  customerName: z.string().min(1, "Namn krävs").max(100),
  email: z.string().email("Ogiltig e-post"),
  quantity: z.number().int().positive("Måste vara > 0"),
});
type OrderForm = z.infer<typeof orderSchema>;

function CreateOrderForm({ onSubmit }: { onSubmit: (d: OrderForm) => void }) {
  const { register, handleSubmit, formState: { errors, isSubmitting } } =
    useForm<OrderForm>({ resolver: zodResolver(orderSchema) });

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register("customerName")} />
      {errors.customerName && <span>{errors.customerName.message}</span>}

      <input type="email" {...register("email")} />
      {errors.email && <span>{errors.email.message}</span>}

      <button type="submit" disabled={isSubmitting}>Spara</button>

}
Varför: React Hook Form minimerar omrenderingar (fälten är "okontrollerade" tills de behövs) — viktigt i stora formulär. Authentication & API-lager

Ett centraliserat API-lager (t.ex. axios-instans) med interceptors som lägger på auth-token och hanterar 401/token-refresh på ett ställe.

// lib/api.ts — en konfigurerad klient för hela appen
export const api = axios.create({ baseURL: import.meta.env.VITE_API_URL });

// Lägg på token automatiskt på varje request
api.interceptors.request.use((config) => {
  const token = tokenStore.get();
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// Hantera 401 centralt — försök refresh, annars logga ut
api.interceptors.response.use(
  (res) => res,
  async (error) => {
    if (error.response?.status === 401) {
      const ok = await tryRefreshToken();
      if (!ok) { tokenStore.clear(); window.location.href = "/login"; }
    }
    return Promise.reject(error);
  }
);
Varför: Ett centralt API-lager gör att auth, baseURL, headers och felhantering finns på ett ställe istället för upprepat i varje fetch. Interceptors hanterar token-refresh transparent så att användaren inte loggas ut i onödan. Lagra helst tokens i httpOnly-cookies (säkrast); localStorage är sårbart för XSS.

Error boundaries & felhantering

En Error Boundary fångar oväntade renderingsfel så att hela appen inte blir en vit skärm — visa istället ett vänligt felmeddelande och logga felet.

// Error Boundary (klasskomponent — enda undantaget från "bara funktioner")
class ErrorBoundary extends React.Component<Props, { hasError: boolean }> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    logToService(error, info);     // skicka till t.ex. Sentry
  }

  render() {
    if (this.state.hasError) return <ErrorFallback />;
    return this.props.children;
  }
}

// Linda in appen (eller enskilda sektioner)
<ErrorBoundary>
  <Routes />
</ErrorBoundary>
Varför: Utan en error boundary kraschar hela React-trädet vid ett oväntat fel och användaren möts av en blank sida — oacceptabelt i en produkt som säljs. Boundaries isolerar felet, visar ett fallback-UI och loggar till en tjänst (Sentry) så att du upptäcker problem hos kunden innan de hör av sig. Kombinera med felhantering för API-anrop (via TanStack Querys error).

Tillgänglighet (a11y)

Tillgänglighet är ofta ett lag-/upphandlingskrav (WCAG/EN 301 549), särskilt för offentlig sektor. Bygg in det från start — det är dyrt att lägga till efteråt.

// ✅ Semantisk HTML — använd rätt element
<button onClick={handleSave}>Spara</button>        // inte <div onClick>
<nav> <main> <header> <footer>                       // landmarks för skärmläsare

// ✅ Labels kopplade till inputs
<label htmlFor="email">E-post</label>
<input id="email" type="email" />

// ✅ Ikonknappar behöver tillgängligt namn
<button aria-label="Stäng"><XIcon /></button>

// ✅ Statusuppdateringar annonseras för skärmläsare
<div role="status" aria-live="polite">{message}</div>

Grunder: tangentbordsnavigering (allt klickbart ska nås med Tab/Enter) · synligt fokus · tillräcklig färgkontrast · alt-text på bilder · inte enbart färg för att förmedla information.

Varför: Tillgänglighet krävs ofta enligt lag (offentlig sektor måste uppfylla WCAG) och utökar din målgrupp. Semantisk HTML ger gratis tangentbords- och skärmläsarstöd — bygger du knappar av <div> tappar du allt det och måste återskapa det manuellt. Att bygga in a11y från start är en bråkdel av kostnaden mot att eftermontera det inför en upphandling.
